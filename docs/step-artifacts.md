# Artifacts Across the 25-Step HTML5 Processing Pipeline

This document tracks the artifacts used by the first 25 processing steps listed in `docs/pipeline-steps.md` (Step 1 through Step 25, ending at **Convert DITA topic to HTML5**).

For each artifact, it captures:

- where it is stored,
- what structure it has,
- which steps generate it,
- which steps consume it,
- which steps modify it in place.

> Note: Step 26 (Convert DITA map to HTML5) is intentionally out of scope because the request was for 25 processing steps.

## Structure details for key artifacts

### A4. Job descriptor (`.job.xml`)

- **Storage:** `${dita.temp.dir}/.job.xml`.
- **Structure:** XML with root `<job>`, `<property>` entries, and file inventory entries that back `ditafileset` and `job.getFileInfo(...)` selections.
- **Why it matters:** It is the central routing table that determines which files each later step sees.

### A7. Key space (`KeyScope`)

- **Storage:** in-memory Java model.
- **Structure:** merged hierarchical key scopes built from map/input-resource key definitions.
- **Why it matters:** Keyref resolution (and mapref follow-up behavior) depends on this model, not only on raw XML files.

### A10/A11. Metadata and link maps

- **Storage:** in-memory DOM/maps while processing, then materialized by rewriting topic/map temp files.
- **Structure:** URI/file keyed maps of metadata/link elements.
- **Why they matter:** They are transient computation artifacts that do not persist as standalone files but still drive large in-place content changes.

### A12. Image metadata

- **Storage:** in-memory image-URI cache during Step 24; written into topic XML as `dita-ot:*` attributes on image elements; file-info format updates persisted via job serialization.
- **Structure:** SAX `Attributes` entries such as width/height/horizontal-dpi/vertical-dpi.
- **Why it matters:** Step 25 reads those rewritten topic files, so image dimensions are already embedded before topic-to-HTML transform.

## Practical takeaways

- Most “artifacts” in this pipeline are **not standalone report files**; many are either:
  - rewrites of temp `.dita/.ditamap` files, or
  - in-memory maps/models that influence those rewrites.
- If you need reproducibility/debuggability, the highest-value persisted checkpoints are:
  1. `${dita.temp.dir}/.job.xml`,
  2. `${dita.temp.dir}` topic/map intermediates before vs. after Steps 15/19/20/24,
  3. final HTML in `${dita.output.dir}`.
